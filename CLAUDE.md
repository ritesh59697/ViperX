## Commands

### Anchor program (`programs/viperx_agent_registry`)

Requires Rust + Solana CLI + Anchor 0.31.1 (pinned in `Anchor.toml` `[toolchain]`). All commands run from `programs/viperx_agent_registry/`:

```bash
anchor build
anchor keys list                          # print program ID
anchor deploy --provider.cluster devnet
anchor test --provider.cluster devnet     # ts-mocha against tests/*.ts
```

`anchor test` runs the whole suite. For a single test, use mocha's grep through the configured script:

```bash
yarn run ts-mocha -p ./tsconfig.json -t 1000000 tests/**/*.ts -g "registers a new agent"
```

Tests import generated types from `../target/types/viperx_agent_registry`, so `anchor build` must run before they typecheck.

### execution-runtime (`backend/execution-runtime`)

```bash
npm run build    # tsc -p .  → dist/
npm run dev      # ts-node src/runner.ts
npm start        # node dist/runner.js
```

`tsconfig.json` only includes `src/**` and `scripts/**`. Needs a `.env` with `RPC_URL`,
`REGISTRY_PROGRAM_ID`, `RUNTIME_KEYPAIR_PATH` (see `src/connection.ts`) — none are defaulted, all
throw loudly if missing.

`npm run dev` starts a real, continuously-running tick loop against devnet once agents delegate
authority to the runtime key. Don't start it casually; it's a standing process, not a one-shot script.

Manual, one-shot Drift devnet vault test (NEXT_STEPS.md step 2 — run this before trusting the
runner against real funds, and re-run it if Drift/Velocity's devnet state changes):

```bash
npx ts-node scripts/drift-devnet-vault-test.ts
```

### pnl-indexer (`backend/pnl-indexer`)

Needs a local Postgres (`createdb viperx && psql -d viperx -f schema.sql`) — no Docker required,
Homebrew's `postgresql@16` works fine. Needs a `.env` with `RPC_URL`, `REGISTRY_PROGRAM_ID`,
`DATABASE_URL` — same fail-loudly-if-missing pattern as execution-runtime.

```bash
npm run dev      # backfills every existing Agent, then listens for registry events until killed
npm run build    # tsc -p .  → dist/
```

### leaderboard-api (`backend/leaderboard-api`)

Needs the same Postgres as pnl-indexer. `.env` needs `DATABASE_URL`; `PORT` defaults to 4000.

```bash
npm run dev      # GET /leaderboard, GET /agents/:agentPda on :4000 (or $PORT)
npm run build    # tsc -p .  → dist/
```

## Architecture

The system splits along a deliberate trust boundary — **on-chain holds only what needs trust guarantees; everything computation-heavy is off-chain.**

- **`programs/viperx_agent_registry`** (Anchor/Rust) — one PDA per agent, seeded `["agent", owner, agent_id]`. Stores owner, agent_id, name, strategy_uri, the Drift vault pubkey, status, trade_count, and `leaderboard_eligible`. `record_trade` bumps the counter and auto-flips `leaderboard_eligible` at `MIN_TRADES_FOR_ELIGIBILITY` (50) — the anti-gaming minimum-track-record rule, enforced on-chain rather than trusted to the frontend. `agent_id` and `vault_pubkey` are immutable by design; everything downstream keys off them.
- **`backend/execution-runtime`** (TS) — polls the registry for `Active` agents delegated to its own key (`registryClient.getManagedActiveAgents()`), runs each agent's strategy loop (`strategies/momentum.ts` is the reference), submits perp trades to Velocity's devnet deployment through a single shared `VelocityClient` (`drivers/velocityDriver.ts`, behind the venue-agnostic `ExecutionDriver` interface in `driver.ts`) using `authoritySubAccountMap` + `switchActiveUser` to trade many different owners' vaults from one runtime key (`runner.ts`), calls `record_trade` after each close. On repeated trade failures the runner disables the agent locally *and* calls the registry's `authority_pause` to flip on-chain status to `Paused` — see Gotchas for why that instruction is safe for a delegated key to hold. **Strategies are caution-aware** (added 2026-08-02) — each of `momentum.ts`/`grid.ts`/`meanReversion.ts` takes an optional `caution` config field (0 upward) that widens its own threshold math (e.g. momentum's `thresholdBps *= 1 + caution`); `strategies/index.ts`'s `createStrategyForAgent` is now `async` and resolves it per-agent via `src/strategyParamsClient.ts`'s `fetchTunedParams()`, a `GET leaderboard-api/agents/:agentPda/params` call that falls back to `caution: 0` on any failure (network, timeout, leaderboard-api down) — never blocks or fails runner startup. Resolved once at strategy construction, not live-hot-reloaded, same "fixed at startup" limitation `runner.ts`'s own agent list already has.
- **`backend/pnl-indexer`** (TS + Postgres) — `registryListener.ts` backfills every `Agent` account then keeps Postgres's `agents` table in sync live via registry events (verified end-to-end, see Gotchas for two real bugs found doing that). `src/velocityWatcher.ts` (added 2026-07-31, verified live the same day) is the Velocity side: a read-only `VelocityClient` (polling `BulkAccountLoader`, same pattern `execution-runtime`'s driver uses) built over every known agent's vault pubkey, watching each one's SOL-PERP `PerpPosition.baseAssetAmount` for a close and reading `PerpPosition.settledPnl` on-chain at that moment to independently compute realized PNL. It doesn't replace `execution-runtime`'s self-report (see Gotchas/NEXT_STEPS.md item 11 for why that exists) — it reconciles against it, writing `onchain_verified_pnl`/`pnl_divergence_flagged` onto the same `trades` row `pnlWrite.ts` already wrote, which `leaderboard-api`'s anti-gaming heuristics now factor in. **Verified against a real devnet close** (`watcher-verify-1`, see NEXT_STEPS.md item 13) — the watcher correctly detected the close within one poll and reconciled it. **Hardened 2026-08-06 after a real attack run found two holes in it** (see Gotchas + NEXT_STEPS.md item 19): it now drains the *whole* backlog of unverified closed trades rather than only the newest one, and uses `UserAccount.nextOrderId` to detect round-trips that opened and closed entirely between two polls — together taking `attack-pnl-divergence.ts`'s detection rate from 2-of-7 to 3-of-3. Schema lives in `backend/pnl-indexer/schema.sql`. **`src/skillEngine.ts`** (added 2026-08-02) is the "agent learns from mistakes" mechanic: a `velocityWatcher`-shaped poll loop (15s, Postgres-only — the live `trades`/`pnl_snapshots` writer is actually `execution-runtime/src/pnlWrite.ts`, not this package's own `metrics.ts`, which only runs at startup backfill, so polling Postgres is the only way to react to a close without new cross-package infra) that (1) unlocks `agent_skills` badges from `src/skillDefinitions.ts`'s static milestone checks (real trade count, sustained Sharpe, drawdown bound — reusing `REAL_TRADE_PREDICATE` so mock trades can't farm them), purely informational in v1, and (2) nudges a single `caution` scalar in `agent_strategy_params` upward when 3+ of an agent's last 5 real trades closed as losses within 60s, logging the reason to `agent_tuning_history`. Deliberately a heuristic, not RL — devnet's near-flat oracle gives no real training signal (see Gotchas), and a heuristic is explainable for a grant demo. **Verified live** (2026-08-02) — running `pnl-indexer`'s real `npm run dev` against real backfilled Postgres data, `skillEngine`'s first poll organically unlocked "Proven Track Record" and "Risk-Aware" for an existing devnet agent with 65 real trades already on record (not seeded), and `leaderboard-api`'s new `GET /agents/:agentPda/params` / extended `GET /agents/:agentPda` (now includes `skills`/`tuningHistory`) were confirmed against real Postgres rows including the `{caution: 0}` default for an untuned agent. The frontend's new Skills/Tuning Log panels on the agent-profile page were confirmed rendering correctly (locked vs. unlocked states, empty-state copy) against a live dev server hitting that same real data. **Both remaining gaps are now closed too** (2026-08-02, same day). The `caution` nudge firing from a real quick-loss sequence: at `watcher-verify-1`'s default $10 size, devnet's near-flat oracle produces PNL swings that round to exactly $0.00 at 2 decimals almost every time — too small a signal for `realizedPnl < 0` to ever see. A new one-off script, `backend/execution-runtime/scripts/verify-caution-trigger.ts` (mirrors `build-track-record.ts`/`generate-micro-trades.ts`'s same production-driver pattern, just with a larger, configurable size), ran real $150 and then $500 open/close round-trips until a natural run of losses landed in the most recent 5 — no rows manually inserted. `pnl-indexer`'s real `npm run dev` then logged `[skillEngine] CLqQSNFHXeoPd3siR2fZxTB31QAyCNid5ymXBpoTutn4 caution 0 -> 0.25 (4 quick losses)`, confirmed against real `agent_strategy_params`/`agent_tuning_history` rows in Postgres. Second gap — `execution-runtime` actually resolving that value into a running strategy's threshold — verified by a second script, `scripts/verify-caution-effect.ts`: it called the real `fetchTunedParams()` against a live `leaderboard-api` (confirmed `caution=0.25`, the exact organically-produced value, not a stub), then fed an identical synthetic 55bps price ramp to two real `MomentumStrategy` instances — one built with `caution: 0`, one with the fetched `0.25`. The ramp crosses the default 50bps threshold but not the widened 62.5bps one: the untuned instance opened a position, the tuned one didn't, on the exact same input. Confirms the whole chain (skillEngine → Postgres → leaderboard-api → strategyParamsClient → strategy construction → strategy behavior) end to end, not just the network hop.
- **`backend/leaderboard-api`** (TS + Express) — `GET /leaderboard` (window-filtered, ranked by `sharpe_like DESC NULLS LAST`, not raw PNL) and `GET /agents/:agentPda`, reading the same Postgres `pnl-indexer` writes. Verified against real backfilled data. Wash-trading heuristics (`src/antiGaming.ts`'s `evaluateAntiGamingHeuristics()`) are implemented and wired into `GET /leaderboard` — flags an agent as wash-traded on 5+ round-trips closed under 10 seconds, over half its trades below a $5 micro-trade floor, **or (added 2026-07-31) 2+ trades where `pnl-indexer`'s independent Velocity watcher observed a different realized PNL than what `execution-runtime` self-reported** — sorting flagged agents below legitimate ones regardless of Sharpe. **The micro-trade threshold is live-verified** (2026-08-01) — a real sequence of 5 sub-$5 devnet trades plus the pre-existing $10 trade on `watcher-verify-1` flipped a real `GET /agents/:agentPda` call to `isWashTraded: true` with `flaggedReason: "Majority micro-trades below $5 minimum threshold"`, not just a clean typecheck (see NEXT_STEPS.md item 16). **The rapid-round-trip and PNL-divergence thresholds are now live-verified too** (2026-08-06, NEXT_STEPS.md item 19) — real attack scripts (`scripts/attack-rapid-round-trip.ts`, `scripts/attack-pnl-divergence.ts`) drove real devnet trades until a real `GET /agents/:agentPda` returned `isWashTraded: true` with, respectively, `"High frequency rapid round-trips detected (5 trades <10s)"` and `"Self-reported PNL diverges from on-chain-verified PNL on 2 trade(s)"`; `watcher-verify-1` stayed correctly unflagged as a control. Caveat worth keeping in mind: the rapid-round-trip rule needs `>= 5` sub-10s trades and got exactly 5, with three of them within 1.5s of the boundary — an attacker holding 11s instead of 9s evades it entirely, so that threshold is validated as *implemented*, not as *hard to evade*. **`GET /leaderboard`'s demotion of flagged agents is confirmed** (2026-08-08) — the earlier "NOT confirmed" note here was a bad test, not a real gap. Two independent filters were being conflated. `routes/leaderboard.ts`'s SQL eligibility gate (`WHERE ($2::boolean = true OR (a.leaderboard_eligible = true AND a.trade_count >= $3))`) runs *before* `rankAndEnrich` is ever called, and both attack agents carry `leaderboard_eligible = false` with 9 trades against a 50 minimum — so they're excluded from the default query by the on-chain minimum-track-record rule, never reaching the scoring path at all. Pass `?all=true` (which bypasses only that gate) and both appear, correctly flagged and sorted to the bottom with `rank: null`: `pnl-divergence-attacker` → `"Self-reported PNL diverges from on-chain-verified PNL on 12 trade(s)"`, `copy-follower-1` → `"High frequency rapid round-trips detected (5 trades <10s)"`, with the four legitimate agents above them unflagged. **Two traps worth not re-deriving**: (1) absence from the default endpoint proves nothing about anti-gaming, since the eligibility gate already removed them; (2) **the list endpoint flattens the anti-gaming fields** to `wash_trading_flagged`/`flagged_reason`/`valid_trade_count`, while `GET /agents/:agentPda` nests them under `antiGaming` — looking for the nested key on the list response finds nothing even when the data is present. The divergence count reading 12 rather than item 19's recorded 2 is the backlog-drain fix working. **`ranked_count` is 2 as of 2026-08-08** — `momentum-sol-2` (PDA `7aFCHFS9…`) was registered, funded, delegated and driven to 51 verified fills specifically to prove the leaderboard ranks more than one agent, and it sits at rank 1 (sharpe 1.00) above `watcher-verify-1` at rank 2 (sharpe -2.60), unflagged. `scoring.ts` requires `verified_trade_count >= 50` on top of `trade_count >= 50`, which is why the three `agent-*` rows still hold no rank: they have `trade_count: 50` from looped `record_trade` calls with **zero** `trades` rows behind them — the exact "increment the counter without trading" attack that gate exists to catch, and the frontend renders it as `0 / 50` verified fills beside a registry count of 50. See NEXT_STEPS.md's 2026-08-08 entry for how the second agent was built (and why the other candidates were unusable). Position-size sanity checks beyond the micro-trade floor are still not built.
- **`frontend`** (Next.js) — create-agent flow (`app/create/page.tsx`) calls `register_agent` directly from the user's wallet; verified with a real Phantom wallet against live devnet (transaction confirmed, account independently re-fetched and decoded to confirm). Once registration confirms, `components/create/FundAndDelegate.tsx` (added 2026-07-23) renders a four-step fund/delegate flow via `hooks/useVelocity.ts` (migrated from `useDrift.ts`): initialize a Velocity account, deposit SOL collateral, delegate trading rights to the execution runtime (Velocity's own `updateUserDelegate`), and separately authorize that runtime key on the registry (`set_authority`) so it can call `record_trade`/`authority_pause` — two different programs, two different delegations. **Verified end to end with a real connected wallet against live devnet** (2026-07-23): fresh registration, all four fund/delegate steps signed and confirmed. `useVelocity.ts` builds its own Anchor `Program<Velocity>` rather than using `VelocityClient` — see Gotchas for why. Leaderboard page (`app/leaderboard/page.tsx`) is a Server Component hitting `leaderboard-api`'s `GET /leaderboard`, window-switchable via plain links; verified against real backfilled data and verified to fail gracefully (no crash) with `leaderboard-api` down. Agent-profile page (`app/agents/[agentPda]/page.tsx`) is a Server Component hitting `leaderboard-api`'s `GET /agents/:agentPda`, linked from each leaderboard row; renders agent stats, trade history, and PNL-snapshot history, 404s via `notFound()` for an unknown PDA, and fails gracefully with `leaderboard-api` down — verified against real backfilled data. **Skills and Tuning Log panels** (added 2026-08-02) render `pnl-indexer`'s `skillEngine.ts` output — a grid of locked/unlocked milestone badges (`frontend/lib/skills.ts`'s `SKILL_LABELS`, hand-duplicated from `skillDefinitions.ts` since the API only returns unlocked ones) and a table of automatic `caution` adjustments — verified rendering correctly against a live dev server hitting real, organically-unlocked skill data (see pnl-indexer's entry above).

Two constraints that shape the design:

- **Keep PNL math out of the Anchor program.** The registry tracks identity, status, and trade count only. PNL is computed off-chain from Drift account data — cheaper, and iterable without touching deployed program logic.
- **Rank by risk-adjusted return, not raw PNL.** Pure PNL ranking gets gamed by high-leverage flukes. This is why the indexer computes Sharpe/drawdown at all.

## Execution venue: Velocity DEX (devnet)

**Migrated from Drift (`@drift-labs/sdk`) to Velocity (`@velocity-exchange/sdk`) on 2026-07-23.** Velocity is Drift's own post-exploit rebuild — not a third-party fork, and not the same thing as the abandoned "pivot to Zeta" idea below. Short version:

- **Why the migration happened:** Drift's shared devnet deployment (program `dRiftyHA...`) had a standing bug where `DriftClient.deposit()` failed for every market with an on-chain `SpotMarketNotFound` error, first found 2026-07-16 and still identical on re-check 2026-07-18 (see the historical Gotcha below and `docs/VENUE-EVALUATION.md`'s addenda). Self-deploying the vendored Drift fork was evaluated and rejected the same day (toolchain breakage plus the reputational problem of running a fork of the exact protocol that lost $285M). - **Verified before migrating, not assumed:** a standalone script (mirroring `drift-devnet-vault-test.ts`'s shape) ran against Velocity's real devnet on 2026-07-23 and confirmed, with real on-chain transactions: `VelocityClient.subscribe()` succeeds and loads spot market 0 (`dUSDT`); a real mint-dUSDT-via-faucet + deposit succeeded (the exact operation broken on Drift's old devnet); `updateUserDelegate` + `authoritySubAccountMap` let a delegate key open and close a real SOL-PERP position on the owner's behalf; a delegate-attempted withdrawal was rejected, preserving the non-custodial model. - **[FIXED 2026-08-02] Arena mode shipped with the Enter Arena modal stuck forever on "Loading your agents..." — a real user-facing bug, found live in the browser, not by typechecking.** Root cause was two independent bugs stacked together: (1) `leaderboard-api` had zero CORS configuration — every prior consumer (`fetchLeaderboard`/`fetchAgent`/`fetchArenaSeason`/etc.) runs inside a Next.js Server Component, server-to-server, which isn't subject to browser CORS at all. `EnterArenaModal.tsx`'s `fetchMyAgents()` call is the *first* fetch that runs client-side in the actual browser, and the browser silently blocked it — no `Access-Control-Allow-Origin` header meant the `fetch()` promise rejected with an opaque, undebuggable `TypeError`. **Fixed** by adding `cors` (`app.use(cors())` in `leaderboard-api/src/index.ts`, before the routers) — permissive is fine here since every mutating route is gated by a real wallet signature, not cookies/session state, so an open origin doesn't hand out any write capability an attacker didn't already have by calling the API directly. (2) Independently, `EnterArenaModal.tsx`'s render logic nested the `status.step === "error"` message *inside* the `myAgents && myAgents.length > 0` block — so when `fetchMyAgents()` threw (from the CORS block, or from any future network failure) and `myAgents` stayed `null`, the error was set but never rendered, and the `myAgents === null` check above it kept showing "Loading..." forever with no way out. **Fixed** by hoisting the error message above the `myAgents`-dependent branches so it renders regardless of whether agents ever loaded. Lesson: a page that only ever fetches server-side (every page before this one) can't hit a CORS problem — the first client-side fetch in a new feature is exactly where it'll surface, and it's worth checking for on sight rather than assuming "it works everywhere else" transfers.

- **[FIXED 2026-07-31] Strategies used to flip their internal `position` state before confirming the driver call actually succeeded on-chain — a failed trade left them permanently out of sync with reality.** Found live verifying `velocityWatcher.ts` against `momentum-sol-1`/`momentum-sol-3`: both agents' shared vault had too little Velocity collateral for a $10 position (`InsufficientCollateral`), and `momentum.ts`'s `onTick()` set `this.position = "long"` (or `"flat"` on close) *before* `runner.ts` ever called `driver.openPosition()`/`closePosition()` — so a failed open still left the strategy believing it was holding a position, and the next tick tried to *close* a position that was never actually opened (`OrderAmountTooSmall`, since the reduce-only order size computed to zero). This oscillated indefinitely between the two failure modes without ever tripping `runner.ts`'s circuit breaker, because an intervening tick where momentum didn't cross either threshold hit the `action: "none"` branch, which unconditionally resets `consecutiveFailures` to 0. **Fix**: `Strategy` (`src/strategy.ts`) gained a `confirmAction(decision)` method — `onTick()` now only *proposes* a decision without mutating position belief, and `runner.ts`'s `handleAgent()` calls `confirmAction()` only immediately after the corresponding `driver.openPosition()`/`closePosition()` call succeeds, never on failure. All three strategies (`momentum.ts`, `grid.ts`, `meanReversion.ts`) had the identical pattern and were all fixed the same way — `grid.ts` also had a `lastTradePrice` mutation that needed the same deferral, via a new `pendingTradePrice` field set in `onTick()` and only committed in `confirmAction()`. A useful side effect: the circuit breaker now trips correctly on a *genuinely* persistent failure (like real insufficient collateral) instead of being neutralized by the old oscillation. Typechecks and builds clean; not yet re-verified live against a real repeated-failure scenario (the original failure that found this was on `momentum-sol-1`/`momentum-sol-3`'s under-collateralized shared vault, still unfunded as of this writing — see NEXT_STEPS.md).
- **[FIXED 2026-08-01] `velocityWatcher.ts` used to only detect a clean flat → open → flat cycle — a direct long-to-short (or short-to-long) reversal that never rests at exactly zero between polls got missed.** First confirmed live during the 2026-07-31 run: after the failed close above, the strategy's next tick opened an opposite-direction order that netted against the still-open position, flipping `baseAssetAmount` straight from positive to negative without an observable zero in between (the watcher polls every 5s; Velocity nets same-market positions rather than stacking them). - **[FIXED 2026-08-06] `velocityWatcher.ts` only ever reconciled the *newest* unverified trade, permanently abandoning every older one — so an agent trading faster than the 5s poll went mostly unverified.** `store.ts`'s `getMostRecentUnverifiedClosedTrade` was `ORDER BY closed_at DESC LIMIT 1`, and its comment assumed "at most one relevant close per agent between polls" with the rapid-round-trip heuristic as a backstop. The real fix for sustained operation is still a dedicated RPC (see the existing "Use a dedicated devnet RPC" gotcha below) — this just stops a transient hiccup from taking the whole loop down while running on the public endpoint.
- **Devnet's SOL-PERP oracle price is nearly flat — real momentum strategies tuned for live-market volatility may never trigger on it.** Sampled directly (2026-07-23): the price moved ~2-3bps over several seconds, then held flat. `momentum.ts`'s real defaults (50bps over a 20-tick window) are appropriate for actual market conditions but can sit silent indefinitely against devnet's low-volatility feed. To prove the runner → Velocity → registry pipeline fires a real trade, the thresholds were temporarily lowered (5-tick window, 2bps) for one run, confirmed a real open → close → `record_trade` cycle, then reverted to the real defaults immediately after — don't leave a hair-trigger threshold running standing, it'll churn gas on every tiny oracle wobble instead of only real momentum.
- **`velocityDriver.ts`'s `closePosition` tied the Postgres trade-write to `registry.recordTrade()` succeeding first — a 429 there silently lost a real closed trade's entire history.** Found live (2026-07-23) wiring up `pnlWrite.ts`: the on-chain close itself succeeded (position genuinely flat, real tx signature logged), but `record_trade` threw on an RPC 429 immediately after — since the Postgres write was sequenced *after* `recordTrade()` with no independent try/catch, it never ran either. Confirmed the loss directly: re-fetched the `Agent` account (`trade_count` unchanged) and queried Postgres (zero `trades` rows for that close) — a real trade happened and left no record anywhere except the raw on-chain transaction itself. Fixed by decoupling: `recordTrade()` and `recordClosedTrade()` (the Postgres write) are now each in their own try/catch, so either can fail independently without blocking the other — a closed position is closed on-chain regardless of what either bookkeeping step does afterward. Also stopped counting either failure toward `runner.ts`'s circuit breaker (`consecutiveFailures`): that counter exists for repeated *trading* failures serious enough to warrant `authority_pause`, not an RPC hiccup in bookkeeping after a trade that actually succeeded. Re-verified live after the fix, under the same RPC pressure that caused the original loss: a subsequent close both called `record_trade` successfully (`trade_count` incremented) *and* wrote a correct `trades`/`pnl_snapshots` row.
- **The three pre-migration Drift debug scripts in `backend/execution-runtime/scripts/`** (`drift-devnet-vault-test.ts`, `inspect-drift.ts`, `test-swap-deposit.ts`) were uncommitted, in-progress debugging work investigating the now-superseded `SpotMarketNotFound` bug — left untouched at first during the 2026-07-23 migration rather than overwritten without asking, then deleted the same day once confirmed they were no longer wanted. `npm run build` is clean again.
- **`backend/execution-runtime/idl/viperx_agent_registry.json` is a vendored copy** of the root `idl/`, kept so this module stays independently deployable (per `docs/ARCHITECTURE.md`) rather than reaching outside its own directory. `registryClient.ts` throws loudly at startup if `REGISTRY_PROGRAM_ID` disagrees with this file's `address` — re-copy from the root `idl/` after any program change, don't hand-edit it.
- **`backend/execution-runtime/drift-protocol-v2/` is a full vendored clone** of Drift's repo, with its own `.git`, tests, and Anchor workspace. It's reference material — don't edit it, and exclude it when searching or the results drown out this project's own code. **Self-deploying it (to stop depending on Drift's broken shared devnet) was evaluated and rejected 2026-07-18** — real toolchain incompatibilities (needs Anchor `0.29.0` via `avm`, `--arch sbf`, hit a Rust nightly-feature-gate failure from an aging dependency graph) plus a standing objection independent of that: it's a fork of the exact protocol that lost ~$285M in the mainnet exploit, and self-hosting unaudited, unpatched code with that history is a bad look for a grant demo built on a non-custodial pitch, not just a technical risk. Full writeup in `docs/VENUE-EVALUATION.md`'s addendum. **Doubly moot after the 2026-07-23 Velocity migration** — the project no longer depends on Drift's devnet at all, so there's no gap left for this to fill even if the toolchain issues were solved.
- **`drift-owner-keypair.json` / `drift-delegate-keypair.json`** are devnet test keypairs, gitignored, auto-generated by `scripts/drift-devnet-vault-test.ts` if absent (previously generated by the now-deleted Zeta script — same filenames, different purpose). **`velocity-owner-keypair.json` / `velocity-delegate-keypair.json`** are the equivalent pair for `scripts/velocity-devnet-vault-test.ts`, added in the 2026-07-23 migration — same gitignored, auto-generated-if-absent pattern. All four are devnet-only; never carry this pattern to mainnet.
- **`target/deploy/viperx_agent_registry-keypair.json` is the program keypair** — it is what makes the program ID `321hJ...`. It lives under the gitignored `target/`, which is correct (it is a private key), but that also means `cargo clean` or a fresh clone destroys it. Back it up outside the repo. Without it you cannot deploy to that address again, and every committed reference to the program ID — `declare_id!`, `Anchor.toml`, `idl/`, and any deployed frontend config — would have to change.
- **Use a dedicated devnet RPC** (Helius/QuickNode) via `RPC_URL` for anything beyond a handful of transactions — public endpoints throttle hard enough to break the execution-runtime loop (confirmed: 50 rapid transactions triggered sustained 429s even with backoff retries). **But Helius's free tier rejects batch RPC requests** (`"Batch requests are only available for paid plans"`), which `BulkAccountLoader`'s polling `accountSubscription` mode depends on — confirmed by hitting a 403 constructing a `DriftClient` against a free-tier Helius key. This applies identically to `VelocityClient`'s polling mode post-migration, same `BulkAccountLoader` class, same dependency. Public devnet RPC tolerated the actual transaction volumes used so far; if a paid Helius/QuickNode plan isn't available, prefer public devnet over a free-tier "dedicated" RPC that silently can't do polling subscriptions at all. **All three major free tiers were tested directly on 2026-08-10 and every one is unusable here — each for a different reason**, which is why `scripts/check-rpc-batching.ts` exists (it probes a real `VelocityClient.subscribe()` with a polling loader, not any single method, and is read-only — no transactions, no funds): **Helius free** rejects JSON-RPC batch requests outright; **Alchemy free** batches fine but withholds `getProgramAccounts` entirely (`"getProgramAccounts is not available on the Free tier — upgrade to Pay As You Go, or Enterprise for access"`), which `subscribe()` needs to enumerate markets; **QuickNode free** ("discover" plan) batches fine *and* allows `getProgramAccounts`, but caps `getMultipleAccounts` at **5 accounts per call** (`code: -32615`), far below what `BulkAccountLoader` requests, so markets silently never load and `subscribe()` resolves with empty state rather than throwing. The pattern: free tiers reserve exactly the heavy account-enumeration methods an indexer needs, and each blocks a *different* one — so "provider X's free tier works" can never be inferred from provider Y, and a shallow liveness check (`getSlot` returns a number) passes on all three. Public devnet remains the best free option: it passes all three probe stages and merely throttles under sustained load, which `runner.ts`'s `unhandledRejection`/`uncaughtException` handlers already mitigate. A genuinely dedicated RPC means a paid plan.
- **Program account resize needs `solana program extend` before `anchor deploy`.** Upgrading a live program doesn't auto-resize its on-chain account; if the new binary is bigger than the allocated space, the upgrade fails with a cryptic `invalid program argument` (Instruction 2) rather than a clear size error. Check current allocation vs new binary size, extend with margin, then deploy.
- **`leaderboard-api` pins Express 4, not 5** — Express 4 doesn't await async route handlers, so an unwrapped `async (req, res) => { await pool.query(...) }` that throws becomes an unhandled rejection instead of a 500; the request just hangs. Every route is wrapped in `src/asyncHandler.ts`. Any new route needs the same wrapper, or upgrade to Express 5 deliberately (it awaits handlers natively) rather than hitting this by surprise.
- **`program.addEventListener()` needs camelCase event names, not the PascalCase from the IDL/Rust — and gets it wrong completely silently.** `BorshEventCoder.decode()` normalizes `AgentStatusChanged` to `agentStatusChanged` before Anchor's `EventManager` does a `Map.get(event.name)` against whatever string was passed to `addEventListener`. Subscribe with the IDL's `AgentStatusChanged` casing and the lookup silently misses forever — no error, the call returns a listener id like normal, the callback just never fires. Confirmed by decoding a real captured on-chain event by hand and reading back `.name`. Also confirmed `connection.onLogs()` and raw `logsSubscribe` both work fine in isolation — this is specifically an Anchor-layer naming mismatch, not an RPC/websocket problem, so don't go debugging the connection layer if events aren't firing. Use camelCase: `agentRegistered`, `agentStatusChanged`, `agentBecameEligible`, `agentAuthorityChanged`.

## Env vars

Each module defines its own (see its README). Common: `SOLANA_CLUSTER=devnet`, `RPC_URL`, `REGISTRY_PROGRAM_ID`, `DATABASE_URL` (indexer/api), `NEXT_PUBLIC_*` mirrors on the frontend.

`NEXT_PUBLIC_RUNTIME_PUBKEY` (frontend, added 2026-07-23) — the execution runtime's own public key (whatever `RUNTIME_KEYPAIR_PATH` resolves to in `backend/execution-runtime/.env`), used by `components/create/FundAndDelegate.tsx` for two separate delegations: Velocity's `updateUserDelegate` and the registry's `set_authority`. No fallback default — it's deployment-specific, so unset disables those two steps in the UI rather than silently pointing at the wrong key.
